## 1 · Goal & purpose

**Goal:** Build a secure API that handles user authentication — Sign Up, Log In, Log Out — and protects specific routes so they answer only for logged-in users. You will use Supabase Auth as your Identity Provider to manage accounts and issue JSON Web Tokens (JWTs), verify those tokens to guard "user-only" endpoints, document the flow in Swagger UI, and publish everything to GitHub.

In your previous assignments your API was wide open: anyone who knew the URL could read, create, or delete data. That's fine for a to-do demo — and a disaster for anything real. A social network only lets you edit your posts; a shop only shows your cart; FlyRank only lets authenticated users see their SEO audits. This assignment is the auth lecture turned into muscle memory: your backend learns who is calling before it decides what to allow.

One deliberate choice runs through the whole task: you do not write cryptography or password-hashing yourself. Rolling your own auth is how careers end — in the real world you lean on a trusted Identity Provider. Supabase stores the accounts, hashes the passwords, and signs the tokens; your job is the part that matters for a backend developer: receiving a token, verifying it, and opening (or refusing) the door.

Beginners usually overthink this. There's no maths and no magic — the entire secured API is a few small routes plus one middleware function, built in stages where you never write more than ~15 lines before you can test again. And it produces the "current user" that next week's tenant-isolation work, and every capstone, depends on.

## 2 · The big idea in 60 seconds

Secure authentication is a trust triangle between three parties: the client, your backend server, and the Identity Provider (Supabase). Nobody trusts a plain password sitting on your server — instead, Supabase vouches for the user by signing a token, and your server checks that signature.

| Step | Who does it | What happens |
|---|---|---|
| 1. Sign up / Log in | Client → Supabase | The client sends credentials (email + password) to Supabase. |
| 2. The token | Supabase → Client | Supabase checks the credentials and returns a JWT (the access token). |
| 3. The request | Client → your server | The client calls your backend, attaching the JWT in an Authorization header. |
| 4. Verification | Your server → Supabase | Your server asks Supabase "is this token real?" If yes, the protected door opens. |

That table is the assignment. Everything below just builds it, one row at a time. Here are the five doors you'll put in the wall:

| Route | Purpose | Auth header |
|---|---|---|
| POST /auth/signup | Create a new user account | none |
| POST /auth/login | Authenticate & return a JWT | none |
| POST /auth/logout | End the user's session | Authorization: Bearer \<token\> |
| GET /protected/profile | Read private profile data | Authorization: Bearer \<token\> |
| GET /public/info | Read public, open data | none |

## 4 · The task — six stages (+ one bonus)

Work stage by stage, in order. Each stage ends with a checkpoint: a command you run to prove it works. Commit to Git after every stage (that's your ≥6 commits, honestly earned). If you only finish Stage 3, submit anyway — a working half is worth more than a broken whole.

**Golden rule for this week:** you never store a password and you never hash anything yourself. Supabase does that. Your code only ever sends credentials to Supabase and verifies the tokens it hands back.

### Stage 0 · Set up Supabase & your server · ~45 min

Before you can guard a castle, you build the guard tower.

1. Create a free account at supabase.com and spin up a new project (call it anything, e.g. *Auth-Practice*). It takes a minute or two to provision.
2. In your Supabase Dashboard, open **Project Settings → API** and copy two values: your **Project URL** and your **anon key** (the public key — safe to use from your app). Never use the `service_role` key here; it bypasses all security.
3. Initialize your project locally and create a git-ignored `.env` for these secrets:
   ```
   SUPABASE_URL=your_project_url
   SUPABASE_KEY=your_anon_key
   PORT=3000
   ```
4. Install your dependencies (framework + the Supabase SDK + a dotenv loader) and initialize the Supabase client from those environment variables. Start the server on your port (Express `3000`, FastAPI `8000`).
5. One-time setting that saves you an hour: by default Supabase makes new users confirm their email before they can log in. For this practice project, open **Authentication → Sign In / Providers → Email** and turn "Confirm email" off, so a fresh signup can log in immediately. (In production you'd leave it on — email confirmation is a real security feature.)

**CHECKPOINT** — run your server. It logs something like `Server running and connected to Supabase` and throws no errors. Your `.env` is already in `.gitignore`.

**Commit:** `Stage 0: setup server and supabase client`

### Stage 1 · Open auth: Sign Up & Log In · ~1 h

The front gates open. Let users register their keys and come back with them.

1. Create `POST /auth/signup`.
   - It expects a JSON body with `email` and `password`.
   - Call the sign-up method — JS `supabase.auth.signUp()` · PY `supabase.auth.sign_up()`.
   - Validate: if email or password is missing, return `400` ("Bad Request") with a JSON error — the server never trusts the client.
   - On success, return `201` ("Created") with the user object Supabase returns.
2. Create `POST /auth/login`.
   - Call the sign-in method — JS `signInWithPassword()` · PY `sign_in_with_password()`.
   - Validate empty fields → `400`. If Supabase rejects the credentials, return `401` with `{ "error": "Invalid login credentials" }`.
   - On success, return `200` with the access token (JWT) and refresh token Supabase provides.

**CHECKPOINT** — register, then log in:
```bash
curl -i -X POST http://localhost:3000/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"password123"}'
```
returns `201`. Then hit `/auth/login` and confirm you get an `"access_token"` string back. Signup with no password → `400`.

**Commit:** `Stage 1: signup and login routes working`

*FlyRank Internship · Backend Track · W2 · A4 — Page 4 of 13*

### Stage 2 · The public & protected gates · ~1 h

Build a public lobby anyone can enter, and a locked door — even before you've hired the guard.

1. Add a public endpoint `GET /public/info`. No auth. Returns `{ "message": "Welcome stranger! This info is public." }` with status `200`.
2. Add a protected endpoint `GET /protected/profile`. To reach it, a client must send their access token in the Authorization header as `Authorization: Bearer <token>`.
   - Inside the route, extract the token from that header.
   - If the header is missing, malformed, or has no token, immediately return `401` with `{ "error": "Access token required" }`. (You're not verifying the token yet — just checking one was presented.)

**CHECKPOINT**
```bash
curl -i http://localhost:3000/public/info       # -> 200
curl -i http://localhost:3000/protected/profile  # -> 401 (no token sent)
```

**Commit:** `Stage 2: public route and unverified protected route`

*FlyRank Internship · Backend Track · W2 · A4 — Page 5 of 13*

### Stage 3 · The guard: token verification · ~1.5 h

The guard at the door inspects the visitor's pass — and turns away forgeries.

Now make `GET /protected/profile` actually verify the token with Supabase.

1. Extract the token from the header (as in Stage 2).
2. Ask Supabase whether it's real — JS `supabase.auth.getUser(token)` · PY `supabase.auth.get_user(token)`. This makes a network call to Supabase, so the answer is trustworthy.
3. If the token is expired, tampered with, or invalid → return `401` with `{ "error": "Invalid or expired token" }`.
4. If it verifies → return `200` with the user's safe metadata (id, email, account-created date).

**CHECKPOINT** — log in, copy the `access_token`, and pass it:
```bash
curl -i http://localhost:3000/protected/profile \
  -H "Authorization: Bearer <PASTE_YOUR_ACCESS_TOKEN_HERE>"
```
returns `200` and your user details. Now change one character of the token and run again → `401`. You just watched a forged pass get rejected.

**Commit:** `Stage 3: profile route token verification`

### Stage 4 · Middleware protection & logout · ~1–1.5 h

One guard, standing at every locked door — instead of the same check pasted into each room.

1. **Middleware guard.** Copy-pasting token-checking into every protected route gets messy and dangerous (miss one, and a door is unguarded). Extract the Stage 3 logic into a reusable middleware function (Express) or dependency (FastAPI). Apply it to `GET /protected/profile` so the route body only runs after the guard verifies the user and attaches it (think `req.user` / the injected user).
2. Create `POST /auth/logout` — a protected route (it uses your new guard). Call the sign-out method — JS `supabase.auth.signOut()` · PY `supabase.auth.sign_out()`. Return `204` ("No Content") on success.
3. Stop and notice: you have built a complete authentication system — sign up, log in, log out, and a single reusable guard protecting any route you point it at.

**CHECKPOINT** — add a second protected route, e.g. `GET /protected/dashboard`, using the same middleware — write no new auth code. Confirm it rejects a bad token with `401` and permits a valid one with `200`. That reuse is the whole point.

**Commit:** `Stage 4: auth middleware and logout endpoint`

### Stage 5 · See it: Swagger UI · ~1 h

So far you've imagined the locked doors. Now put visible padlocks on them.

Swagger UI turns your API into an interactive page with a *Try it out* button — and a lock icon that lets you paste a token once and reuse it. You just have to tell it which doors are locked.

- **Python lane:** FastAPI already serves Swagger at `http://localhost:8000/docs`. To make the Authorize padlock appear, configure FastAPI's `HTTPBearer` security scheme and apply it to your protected routes.
- **JavaScript lane:** in your `openapi.json`, define a `securitySchemes` block of `type: http`, `scheme: bearer`, `bearerFormat: JWT`, and link it to your `/protected/` and `/auth/logout` endpoints. Serve it with `swagger-ui-express` at `/docs`.

Then, in the browser: click **Authorize**, paste a JWT from your login, and run **Try it out** on `GET /protected/profile` — no curl needed.

**CHECKPOINT** — `/docs` shows a lock icon next to your protected routes; you can authorize with a token and successfully call the profile endpoint from the browser. Take a screenshot of Swagger for the README.

**Commit:** `Stage 5: Swagger UI documentation with bearer auth`

### ★ Make it yours — optional extras · optional · as many or as few as you like

You have real user accounts now — do something with them.

None of these are required. Pick whatever sounds fun (creative alternatives welcome):

- **Read the token yourself:** paste an access token into [jwt.io](https://jwt.io) and look at the decoded payload. Write two sentences on what's inside a JWT — and why you never put a secret in one (anyone can read it).
- **The expiry experiment:** log in, wait for the access token to expire (Supabase default: one hour), then call `/protected/profile` with the stale token. Note the `401`. This is the entire reason refresh tokens exist.
- **A 403 case:** add a route a logged-in user can reach but only an "admin" may use; return `403` ("Forbidden") for everyone else. `401` = "I don't know you"; `403` = "I know you, and no." That difference is authorization.
- **A real logout test:** log out, then reuse the same token on a protected route and record what happens — why stateless JWTs make "instant logout" genuinely hard.
- **Refresh flow:** use the refresh token from login to obtain a new access token without logging in again.

## 5 · Bonus stage — the AI rematch · ~1 h · optional — and the most fun

### Stage 7 · The AI rematch

You secured an API by hand, door by door. Now hire the fastest junior developer on Earth to do it — and review their work.

You did Stages 0–6 by hand for a reason: you now know exactly what a correct, secure auth flow looks like. That knowledge turns this stage from a magic show into a code review.

1. Write the **prompt** yourself — this is the real exercise. Without copying from this document, write your own prompt asking an AI to build the same secured API. From memory, specify: your lane and framework, Supabase as the Identity Provider, the five routes, the status codes (`201` / `200` / `204` / `400` / `401`), token verification via middleware, and the Swagger bearer setup.
2. Generate in quarantine. Put the AI's code in a separate folder (`ai-version/`) or branch. Your Stages 0–6 code stays untouched — that is your submission.
3. Run it. Does it start? Fire your Stage 3 and Stage 4 checkpoints at it — a valid token, then a tampered one.
4. **Diff** it. Compare with yours (`git diff --no-index your-file ai-file`), then answer three questions in an "AI vs me" README section:
   - How did it handle token extraction — did it correctly parse the `"Bearer "` prefix, or would `Authorization: <token>` slip through or crash?
   - What security flaws might it have introduced — does it safely reject an invalid token, or trust `getUser` without checking the error? Did it leak the `service_role` key or log the token?
   - What did your prompt forget to specify — and what did the AI silently decide for you?
5. One rematch. Improve your prompt with what you learned, regenerate, and note in one sentence what changed.

The lesson hiding in this stage: an AI's output is exactly as good as your specification — and you could only judge it because you built the thing yourself first. Both halves of that sentence are your career from now on.

**CHECKPOINT** — your README has an "AI vs me" section with your full prompt and ≥3 concrete differences.

**Commit:** `Stage 7: AI vs me (AI code stays in its own folder/branch).`

## 9 · Glossary

Plain-language definitions of every bold word above. No definition depends on another — read them in any order.

| Word | What it means |
|---|---|
| API | The set of doors your program offers so other programs can talk to it — here, the five auth/profile endpoints. |
| Authentication | Verifying who a user is (matching an email and password). The question `POST /login` answers. |
| Authorization | Verifying what an already-known user is allowed to do. The question a `403` answers. |
| Identity Provider (IdP) | An external service — Supabase here, or Auth0, Firebase, Google — that manages accounts, passwords, and tokens so your server never has to. |
| Supabase Auth | The authentication part of Supabase: it stores users, hashes passwords, and issues signed JWTs. You call it; you don't reimplement it. |
| Credentials | The email and password a user proves themselves with. Your server forwards them to Supabase and never stores them. |
| JSON Web Token (JWT) | A compact, signed string that carries claims (like "this is user 123"). Because it's cryptographically signed, it can't be secretly altered — change one character and verification fails. |
| Access token | The specific JWT a client sends on each request to prove it's logged in. Short-lived (Supabase's default is one hour). |
| Refresh token | A longer-lived token used to get a new access token when the old one expires, without making the user log in again. |
| Bearer token | Any token the server honours for whoever "bears" (presents) it, sent as `Authorization: Bearer <token>`. Your access token is used as a bearer token. |
| Authorization header | The standard HTTP header a client uses to send a token: `Authorization: Bearer eyJhbGciOi...`. |
| Protected / protect | A route that runs its logic only after a valid token is verified; without one it answers `401`. |
| Middleware | A function that runs before your route handler and can stop the request early. Your auth guard is middleware: it verifies the token, attaches the user, then lets the route run. |
| Dependency (FastAPI) | FastAPI's version of middleware for a route: a function FastAPI runs first (to verify the token) and injects its result into your handler. |
| Extract (a token) | To pull the token string out of the `Authorization: Bearer <token>` header before verifying it. |
| Validate / validation | Checking incoming data before trusting it — here, that email and password are present — and rejecting bad input with `400`. |
| Status code | The 3-digit number in every response saying how it went: `200 OK` · `201 Created` · `204 No Content` · `400 Bad Request` · `401 Unauthorized` · `403 Forbidden` · `429 Too Many Requests`. |
| 401 vs 403 | `401 Unauthorized` = "I don't know who you are" (missing/bad token). `403 Forbidden` = "I know exactly who you are, and you still may not." |
| Environment variable / .env | A configuration value handed to your program at startup. Secrets like your Supabase keys live in a git-ignored `.env` file, never in code. |
| .env.example | A committed copy of `.env` with the key names and placeholder values, so a teammate knows what to set without seeing your real secrets. |
| anon key | Supabase's public API key, safe to use from your app. Distinct from the `service_role` key, which bypasses security and must stay server-side and secret. |
| Supabase Dashboard | Supabase's web console where you find your Project URL and keys and change auth settings (like turning off email confirmation). |
| Swagger UI | A web page that renders your API as interactive docs with a "Try it out" button and, once configured, an "Authorize" padlock for pasting a token. |
